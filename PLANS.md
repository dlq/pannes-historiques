## Storage And Retention Plan — proposed, 2026-11-01

Status: planning only; no new production scan, export, migration, retention job or deletion was performed for this plan. Priority: establish the measured storage/recovery boundary before adding Westmount or notification state. This plan preserves existing archive behavior first; event reclassification and metric corrections are the separate identity/API work below. Existing ADRs 0003/0005 remain in force until a reviewed implementation decision explicitly supersedes the relevant parts.

### Baseline, risks and preservation contract

- Last recorded D1 size: `3,355,394,048` bytes on November 1, approximately 250 MB above October 22. That dated measurement is not a live table-size inventory or a reliable long-term forecast. 3.5 GB is the project's internal review/action trigger; 4 GB is the existing migration-action threshold. Neither is the platform failure limit. Cloudflare currently documents a 10 GB paid-plan database limit and first 5 GB included storage; confirm actual account terms and limits before executing a migration. Sources: [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [pricing](https://developers.cloudflare.com/d1/platform/pricing/).
- Observed schema: `hydro_polygon_geometries` stores both normalized GeoJSON and raw coordinates for each source version/polygon. `previous_outage_territory_bins` repeats assignment/territory and derived metric data per snapshot polygon. `resolved_events` also accumulates source-version strings. These are storage candidates, not measured attribution; indexes, other tables and free-page reuse must be measured before selecting the biggest saving.
- Old current/planned marker rows are already pruned, raw feeds live in R2, terminal ingestion runs retain 30 days, stranded runs expire after three hours, and geocode-cache rows retain 30 days. Preserve those working policies; do not claim them as new savings. Usage aggregates retain 90 days under ADR 0007.
- Important replay dependency: `outageStatsForPolygon()` currently joins marker rows for the same source version and falls back to `eventCount: 1`/an observation-time label if none remain. Raw-input retention alone does not prove that a later rebuild reproduces the original derived bin values after marker pruning. Exact existing rows and build/parser/territory versions must be preserved or reproducibly reconstructed before replacement.
- Preserve all currently supported address-history lookbacks, map geometry/detail behavior, municipal assignments, existing count units, archive windows/charts/latest/largest results, attribution, raw provenance and known gaps. ADR 0005's one-year summary guarantee is a minimum, not authorization to discard older history or shorten a longer UI/API lookback. No silent change to outage counts, spatial precision, resolution semantics or source coverage as a storage optimization.

### Phase S1 — select and document the physical model

Recommended order, conditional on S0 measurements:

1. Deduplicate unchanged geometry and eliminate reconstructable duplicate coordinate text from hot D1 storage, retaining the original bytes in R2 and exact version-to-geometry references.
2. Compact repeated assignment/provenance metadata without changing any existing metric, retaining observation/assignment records and immutable legacy exports.
3. If those savings do not provide sufficient durable headroom, offload immutable older geometry/observation/assignment partitions to R2, retaining a bounded spatial/time catalog and the materialized products needed for current public reads. A lossy monthly total alone cannot replace arbitrary-radius/date history or largest/latest queries.

- [ ] Compare geometry-only dedup, combined dedup/lean assignments and cold R2 partitioning on the same local dataset. Include new index/reference overhead, CPU/reads, R2 GET/PUT amplification and rollback copies; choose the smallest change that meets the measured budget. Splitting databases is a separately measured option, not a way to ignore growth or move it beyond a dashboard threshold.
- [ ] Proposed schema boundary: immutable geometry objects with exact canonical digest plus raw-source/parser references; lean snapshot/feature→geometry links; normalized territory identity/version; lean observation→territory assignments; immutable archive partition manifests; and an atomic published archive-generation pointer. Keep published historical identities stable during physical relocation. Do not use mutable array positions or new semantic episode IDs as migration keys.
- [ ] Define versioned canonical geometry encoding, CRS, numeric precision, ring/hole/multipolygon behavior and digest algorithm. Preserve exact parsed geometry for containment/provenance. Deduplicate only verified equivalent representations; do not round/simplify geometry to get a better compression ratio. Display simplification stays a separately named derivative with measured error.
- [ ] For cold offload, choose chunk format/size and spatial/time partitioning from observed queries (compressed JSON/NDJSON with bounded decoded size is the first candidate). Store precise immutable row-level legacy representations and lineage, plus indexed bounds/time ranges and hashes. Define read fanout/CPU/byte caps, cross-partition merging and pagination before moving anything. R2 is object storage, not a relational query engine; never scan the bucket on a public request.
- [ ] Keep current feeds and recent working sets hot; choose any hot-age cutoff from query measurements rather than silently declaring old history unavailable. Public full-coverage reads must reach the cold tier where required. For a date/radius that exceeds safe fanout, return an honest bounded-query response rather than a partial result labelled complete; preserve existing supported UI behavior through suitable materialization/indexing before cutover.
- [ ] Proposed acceptance budget to confirm after S0: post-migration D1 at or below 3.0 GB and at least 90 projected days before 3.5 GB at a conservative measured growth rate, with no unexplained archive regression. If geometry-only work misses that budget, continue to measured offload or choose a documented alternative; do not close retention planning on a small one-time shrink. Write concrete request-latency, R2-fanout, row-read/write and monthly-cost budgets before implementation, comparing with the recorded baseline.
- [ ] Record the selected physical model, retention exceptions, reclaim strategy and deletion conditions in a successor/amendment to ADR 0005 during implementation. A plan is not an accepted architecture decision. Update `docs/architecture.md`, operations and public disclosure where behavior/storage boundaries actually change.

### Phase S2 — replayable build and safe publication

- [ ] Create additive schema and a resumable offline/maintenance builder with an immutable job specification, source high-water mark, fixed parser/territory/build versions and indexed keyset cursor. No giant one-transaction rewrite. Bound rows, bytes, elapsed time and costs per batch; checkpoint only after durable writes. Repeating a batch must not increase event/observation counts or duplicate membership rows.
- [ ] Preserve exact original derived rows into checksummed immutable chunks before transforming them, especially where old marker rows are gone or a legacy calculation cannot be reproduced from available inputs. Rebuild-from-raw and preserving legacy materialization are separate paths; compare them and document differences rather than silently choosing a new number.
- [ ] Build new geometry references/partitions/manifests off the request path. R2 upload → verify hash/count/read/decode → commit D1 catalog/staged rows → atomically advance one published generation only after every component is complete. R2 consistency does not provide an atomic transaction with D1 or CDN caches; immutable object names and a single D1 publication boundary are still required. [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).
- [ ] Keep old readers/writers operational during bulk build. Capture a starting watermark, then replay the ingest tail into the new store or dual-write through an idempotent adapter. At final cutover acquire a bounded publication lease, drain/record the tail and atomically publish compatible cursors/read configuration. Raw collection can continue during a short normalized-publication pause; never discard versions received during migration.
- [ ] Rebase numeric/compound archive cursors through explicit old→new mappings, not a count or lexicographic guess. Check no skipped/duplicated polygon, unassigned/outside-territory classifications and summary source-cursor coherence. Pinned in-flight readers must see one generation, not old counts paired with new geometry.
- [ ] Prove peak-capacity safety before starting: existing tables + shadow references/objects/indexes + temporary rebuild/export overhead + expected ingest growth + rollback hold. A same-database table rebuild may temporarily use far more space than the final layout. If it exceeds headroom/budgets, use a staged offload or separately authorized replacement database and binding cutover; do not run the old large-table-copy strategy blindly.

### Phase S3 — parity, cleanup and measured reclamation

- [ ] Compare all legacy/staged row counts by provider/source/time partition, geometry checksums/equivalence, assignment types, nulls, retained versions/gaps and raw-object resolvability. Counts alone are insufficient: compare deterministic row hashes and selected full records. No unmatched rows or broken references outside an explicitly recorded pre-existing gap.
- [ ] Compare actual query results for dense/sparse/border/hole/multipolygon addresses and all existing UI time/radius windows, municipal/province summaries, largest/latest rows and raw provenance. Preserve exact values/ordering under the legacy metric definition; do not “fix” unit/grouping errors in the storage migration. Carry known semantic limitations forward with labels until the separately reviewed identity correction.
- [ ] Run fault/restart checks: partial R2 upload, failed D1 batch, missing/corrupt chunk, stale catalog, lease expiry, ingest during build/cutover, repeated tail replay and worker rollback. A failed read is unavailable/stale, never an empty archive or a forced request-time rebuild of the full dataset.
- [ ] Canary/shadow read comparisons first, then explicitly authorized reader cutover. Observe at least seven complete days of ingestion/summary/ordinary reads, plus the agreed 14-day rollback hold before removing old payloads. Avoid daily full production audits: do comprehensive checks locally/staging and bounded production canaries with full checkpoint manifests.
- [ ] Cleanup is a distinct reviewed step with exact eligible IDs/ranges, retained replacement manifests/checksums, estimated savings and restore plan. Default to dry-run. Remove only verified unpinned derived duplicates in bounded batches; no raw-source, history or private-data policy expansion hidden in a generic cleanup function.
- [ ] Verify actual D1 size/free-page reuse and rows read/written after cleanup. A DELETE count is not evidence that billed/physical database size decreased. Test supported reclamation behavior on staging; do not assume `VACUUM` works remotely. Use a tested bounded rebuild/replacement-db path if needed, with account-specific limits and migration cost reviewed first. Never issue an unbounded production delete/rebuild to force a size graph downward.
- [ ] Add cheap weekly size/growth forecasts and threshold warnings to existing operations, with monthly cost/recovery checks. Monitor archive completeness/cursors and raw-replay checks separately. A healthy ingestion endpoint does not establish that archival reconstruction or backup restore works.

Recovery and rollback: before cleanup, revert the reader-generation pointer and compatible writer configuration, then replay any captured tail. After cleanup, restore the immutable legacy partitions/new-store checkpoint and rehearse reconstruction in isolation; use a whole-D1 Time Travel restore only with a plan for writes since the bookmark, source replay and private deletion/expiry records. Do not resurrect deleted notification/user data through a bulk restore; retain/reapply deletion tombstones under the private-data policy. A rollback must preserve both the old public information and post-checkpoint observations, not merely make the homepage load.

Implementation slices: S0 inventory/restore tooling and evidence → selected-model ADR/fixtures → additive storage and resumable builder → shadow readers/tail parity → explicitly authorized cutover → separately authorized eligible cleanup/reclamation. Relevant files include migrations, `src/worker.js` storage/ingest/backfill paths, `src/municipal-archive.js`, `src/archive-summary.js`, `src/durable-read-handlers.js`, Python fallback readers and maintenance tooling. New helpers remain under their runtime boundary; choose migration numbers from the implementation head.

Verification: real local/staging D1/R2 integration tests for publication/replay/deletion and fault recovery; Python/Node parity fixtures and archive coherence tests; full pre-commit, Python, Node and Playwright suites for reader/service changes, plus actual desktop/mobile Archive/history checks. Run Wrangler dry-run and representative migration/restore drills before any authorized production action. Exit requires preserved query/provenance behavior, measured reclaimed/headroom budget, bounded ongoing growth/cost, functioning recovery, and no automatic destructive policy beyond the accepted ADR.

### Observed implementation and the decisions it cannot support yet

- HQ live rows currently use `bis:<source_version>:<record_index>` / `aip:<source_version>:<record_index>`. These locate a row in one source version; they do not identify one physical outage across snapshots. The planned feed exposes a `notice_id` field, but its uniqueness, reuse and schedule-revision lifecycle still need validation.
- `resolved_events` is upserted while ingesting current/planned sightings. Its name does not establish actual restoration. The current Worker grouping key combines kind, municipality, centroid rounded to three decimals, interruption type and a minute-level start-time string; estimated restoration can be stored in generic `end_time`. `record_count` increments on every upsert, and comma-separated `source_versions` carries provenance. These are legacy heuristic groupings, not proven utility incident identity or replay-safe counters.
- Python builds a similar key using `round()` and default float stringification; Worker uses fixed-width `toFixed(3)`. Equivalent coordinates can therefore serialize differently. Also audit planned-time mapping: Python's initial generic `end_time` reads column 2, while the Worker planned branch reads column 3. These are code-review observations requiring focused characterization tests, not claims that a particular live record/user answer was wrong.
- Existing map geometry/render grouping is another identity (including a coarser centroid-based previous-layer grouping), and municipal bins identify a polygon sighting/territory assignment. Do not treat every UI render group, archive bin, retained sighting, notification candidate and source incident as interchangeable.
- Westmount provides network-block identity/status; no upstream incident ID was established. Source timestamps and the client-count meaning remain under its separate validation gate. Saved-area notifications require stable correlation/dedup before they can safely alert across source updates.

### Shared vocabulary and identity types

| Concept | Proposed identity and meaning | Explicit non-guarantee |
| --- | --- | --- |
| Provider/source definition | Stable provider key plus source/layer definition version and identity epoch where upstream IDs can be reused. | A municipality name is not a distributor or exclusive service territory. |
| Raw snapshot/publication | Provider/source + immutable publication manifest, containing upstream version/identity epoch and content digest/revision; separate fetch-attempt metadata. Exact blobs deduplicate by digest, while distinct claimed publications retain separate references. Preserve different bytes even if the upstream reuses a version label. | A source version string or successful fetch does not prove current/comprehensive upstream data. |
| Observation | Opaque immutable ID bound to a raw snapshot and exact record locator. A locator may use an index **inside those immutable bytes**; parser output has a separate revision. | This does not identify a physical outage across snapshots; a parser replay is not a new sighting. |
| Source entity | Provider/source/epoch + verified persistent native ID (e.g. Westmount block or validated planned notice). | Block/notice existence is not an outage incident; a removed/reused ID is not the same entity automatically. |
| Inferred episode | Persisted opaque ID plus derivation version and linked observations describing a conservatively correlated period/entity state. | It is not an official utility incident ID; ambiguous merge/split/reopening remains explicit. |
| Geometry | Exact canonical geometry digest/version, separate from immutable raw/source geometry IDs and display derivatives. | Same geometry does not mean same incident; changing geometry does not by itself mean a new incident. |
| Published dataset generation | Immutable manifest of provider/product component cursors and parser/model/territory versions; readers pin one generation. | Multiple upstream resources need not have been captured at one atomic instant; include their capture ranges. |

Proposed public IDs are opaque and provider-qualified in the resource envelope; no raw address, coordinate or heuristic centroid/time string in an identifier. Use a persisted mapping, not a recalculated mutable semantic hash, for episode/public identity. Internal hashes still require versioned canonicalization and collision/multiplicity handling. Preserve raw source IDs separately as qualified provenance only when suitable for public release.

Record capture start/end, because a paged source need not provide a transactionally frozen snapshot. Check ID-set/count consistency and quarantine unexplained membership changes; never interpret a disappearing block as restored service.
- [ ] Archive exact response pages and relevant public headers, endpoint/query definition, timestamps, source metadata, digests and parser version in R2 under a provider prefix. Use content hashes to deduplicate unchanged bodies; link successful poll/validation metadata to the retained bytes. Store only selected public fields under the approved retention contract; never persist credentials/cookies.
- [ ] Sequence publication: validate complete response set → persist R2 inputs → write immutable D1 snapshot metadata and staged derived rows → atomically advance the provider's generation pointer. Failed writes leave the last good generation visible. Readers pin one generation. Use a provider run lease/idempotency key to prevent overlapping cron/retry publication and duplicate observations; retry/replay converges on the same result.
- [ ] Diff against the last accepted provider generation and write state observations only on meaningful changes; keep a cheap poll heartbeat for successful unchanged responses. Record missing/unknown source state explicitly. Preserve raw/message changes according to the field contract even when the main status code is unchanged.
- [ ] Give Westmount a separately enabled schedule/run name and source summary. It must execute independently of Hydro's container job; either can fail without preventing the other from running. Collection runs directly in the Worker and persists to D1/R2; it must not wake the container or write durable state there.

Cost gate: at a five-minute interval, a single attributes request is about 288 polls/day, inspecting roughly 67,392 block rows/day at the observed 234-block baseline. This is an upstream-work estimate, **not** a D1-write estimate. Measure response bytes, R2 writes/storage, changed rows, geometry sizes and Worker/D1 cost in a representative run. Avoid appending 234 full D1 rows per poll or duplicating geometry per observation. Resolve the current storage headroom concern before adding an unbounded production archive; retain raw data/provenance per ADRs 0003/0005.

### Phase 3 — provider health and private shadow validation

- [ ] Expose per-provider operational status: enabled/shadow/public, latest attempt, last complete validated fetch, source-reported update time, failure streak, last good generation, collection start, and known gaps. Distinguish collector health from upstream freshness confidence: a successful empty response or an unchanged old `LastUpdate` is neither proof of a broken feed nor proof that the upstream producer is fresh.
- [ ] Proposed starting alert policy, to tune against the accepted cadence: stale after three missed five-minute intervals (15 minutes), alert after three failed runs, with a clear no-success state. Do not reuse Hydro's three-hour allowance without a source-specific decision. Scheduled failures must not advance the successful-validation timestamp.

Add assertions to the existing hourly GitHub health monitor, without creating another monitoring service.
- [ ] Preserve last good features during failures, marked stale with collection time and official referral. Do not turn errors into an empty map/no-outage answer. Add bounded run retention and actionable transition-based monitoring; avoid logging full payloads on every poll.
- [ ] Run a separately authorized private shadow period of at least seven days. Compare a few sampled responses with the official map; record source changes, field completeness, unknown codes, boundary membership, polling success and cost. Healthy-only observations can validate availability but do not validate outage/restoration semantics. Require an actual incident transition or operator-confirmed nonempty examples plus replay evidence before promoting those semantics.

Exit: zero unexplained partial-publication events, no false all-clear in fault tests, replay/idempotency confirmed, documented source freshness limitations and accepted cost/retention budget. A quiet week is not proof of archive completeness or ongoing outage accuracy.

## Saved-Area Web Notifications Plan — proposed, 2026-11-01

Status: detailed planning, not implemented or scheduled. No subscription, notification, new cloud resource, tracking change or deployment is authorized by this document. This replaces the vague notification-backlog entry with a concrete proposal; readiness/privacy/cost gates still apply. The user has requested this plan, which establishes interest but does not establish broader adoption demand or production readiness.

### Product outcome and first-release boundaries

Save a few locations from the existing address/map flow and optionally receive a browser notification when a new outage is observed nearby. Keep the map and sheet as the primary interface; add a small saved-areas list and per-area notification controls rather than a new dashboard or navigation redesign.

Proposed defaults, subject to validation before implementation:

- Up to five saved areas per browser installation. Store a chosen center and one of the existing 1/2/5/10 km radii (2 km default for a typed address), a local display label, language and source-coverage choices. Show the radius and coverage before saving; a nearby alert is not proof that the selected residence lost power.
- Saved areas work **locally without an account or notification permission**. Labels/typed addresses stay on the device. No automatic conversion of the current six-item comparison tray or search history into saved/server-monitored locations.
- Explicit notification opt-in uploads only the monitoring geometry/radius, provider preferences, minimal device-management credential and push-subscription material. Explain that these data must remain on our server to match outages while the site is closed. Saving locally and enabling remote monitoring are separate actions.
- First alert type: newly observed ongoing outage near an enabled area. Start with Hydro-Québec, whose production collection already exists; Westmount is eligible only after its own source/semantics/public-launch gates pass. Do not make this feature depend on Westmount implementation, or silently enroll a newly supported provider into an existing area's alerts.
- Planned-interruption notices/reminders, restoration messages and material restoration-estimate changes are later, separately enabled alert types. No email/SMS, accounts, cross-device sync, background location tracking, social notices, historical backfill alerts or emergency/guaranteed-delivery promise in the first release.
- Default notification text is generic enough for a lock screen: an outage was observed near a saved area; open pannes.ca for the details and checked time. Do not include an address, local label, precise coordinate or assertion that power is off/on at home. Users may later opt into a more descriptive label after seeing a privacy preview.

### Baseline and platform constraints

Observed in the repository: `app/static/search.js` registers the service worker and stores a browser-local comparison tray. `app/static/service-worker.js` currently handles installation/activation and an offline navigation fallback only. A manifest already exists at `app/static/manifest.webmanifest`, linked from the shell with standalone/scope/installability tests. There is no saved-area subscription model, permission flow, push handler, push sender or notification route.

- Implement standards-based Push API/Web Notifications with a service worker, VAPID and encrypted payloads. Browser push services relay delivery; “first-party feature” does not mean no third-party transport. Select a maintained Worker-compatible Web Push implementation after a small compatibility/dependency audit; do not implement message encryption/signing from scratch or wake Flask to send pushes. Reference: [W3C Push API](https://www.w3.org/TR/push-api/) (currently a working draft) and [Apple Web Push documentation](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).
- Permission is requested only after the user deliberately enables alerts. Show coverage, upload disclosure and platform requirements first. No permission prompt on arrival, saving an area, or reopening a denied permission. Use capability detection and a usable local-only state for unsupported/denied browsers.
- For iOS/iPadOS, plan and test the Home Screen web-app path and permission request from a direct user gesture; an ordinary browser tab is not an equivalent delivery test. Revalidate current browser/OS support at implementation time rather than promising support from user-agent strings. [WebKit guidance](https://webkit.org/blog/13878/).
- OS/browser permission, Focus settings, offline devices, push expiry and upstream collection cadence affect delivery. Existing HQ polling is about every 15 minutes; a faster push dispatcher cannot make source observations instantaneous. Show “observed nearby,” not “just started,” and distinguish provider acceptance from actual device display.
- Do not rely on browser background timers, Background Sync availability, an open tab or silent push as a general heartbeat. Each real push must produce a visible notification; use `userVisibleOnly` and appropriate visible handling. Do not use silent messages for analytics or background location collection.

A random public area/subscription ID is not authorization. Bind every list/read/update/delete/test request to the enrollment owner; implement cross-owner tests. No GET mutation, secret-bearing query string or cacheable private response.
- [ ] Proposed API surface: enrollment/status, area CRUD, subscription upsert/reconcile, pause/resume, rate-limited test notification and delete-all. Validate request size and allowed fields; return minimal state with `Cache-Control: no-store`. Keep addresses, coordinates, push endpoints, keys and credentials out of URLs, access/error logs, exception traces, usage events and public health output. Keep typed address/display label local. - [ ] Implement a visible enrollment confirmation/test, browser/server reconciliation on app open, permission revocation, expired endpoint cleanup and subscription renewal without relying solely on `pushsubscriptionchange`. ### Regression guard: gated runtime endpoints (2026-08-05)

The Contexte tab was empty for seven weeks and nobody noticed. `34fee84`
(2026-06-17) gated both `GET /map-context` and `GET /previous-archive-summary`;
the container cannot authenticate, so both broke that day. `7300355`
(2026-06-20) ungated `previous-archive-summary` while working on the archive,
which fixed Archive and left Contexte broken. The same bug was found and fixed
once already, on a sibling endpoint, without anyone checking the siblings.

Why every existing safeguard missed it:

- The failure rendered as plausible content ("Aucun document publié disponible"), not as an error. A broken data path and a genuine empty result were indistinguishable.
- The map still drew region outlines from the static geometry asset, so the tab looked alive.
- The Worker logged `Ok`: returning `404` to an unauthorized caller is correct behaviour. Nothing looked wrong from either side.
- `runtime-policy.test.js` asserted that the gate list contained what the gate list contained. That tautology passes regardless of whether the container can actually reach the endpoint.

Rules that follow from this:

1. Never let a failed read render as an authoritative empty state. Distinguish "the lookup failed" from "there is nothing", and say which. Applied to the published-context builders; apply it to any new remote read.
2. Never cache a failed read. `_cached_context` without `ttl_seconds` caches forever, so one transient failure becomes permanent. Pass a TTL and a `should_cache` predicate.
3. Adding an endpoint to `PRIVATE_RUNTIME_ENDPOINTS` requires proving the container can still reach it, because the container currently cannot authenticate at all.
4. Prefer end-to-end assertions over policy-table assertions. A test that reads the same constant the code reads proves nothing about reachability.
5. When fixing a broken endpoint, check its siblings for the same defect before closing the work.

### Regression guard: figures that contradict each other (2026-08-05)

The Archive report showed a count of municipalities where it said outages. The
`1 an` cell read `1 139` against 234 187 retained outages, and the customer sum
beside it read 22 290 686 against roughly 4.5 million Hydro-Québec customers.
Montréal's own row read 16 785 outages — a part larger than the stated whole,
on the same screen, for months.

Why every existing safeguard missed it:

- Every test asserted a number equalled what its query returned, and every query returned exactly what it was asked for. A query answering the wrong question passes all of them.
- The payload field was named `areas`. The other summary path filled that same key with a genuine outage count, so the name was honest for one caller and misleading for the other.
- Local development runs the honest path, so local figures looked plausible while production did not. Any check performed only locally would have confirmed the bug as correct.
- Nothing compared the figures to each other. Each was individually defensible; only their relationship was impossible.

Rules that follow from this:

1. Assert displayed figures against each other, not only against their source query. Self-comparison needs no expected values and no thresholds, so it survives data changes.
2. A field name is part of the contract. If two code paths fill the same key, they must compute the same quantity — enforced for the archive windows by a test.
3. Run coherence checks against real data, not only fixtures. Fixtures guard the code; only production data catches the data. These run inside `GET /api/health/ingestion`.
4. Prefer invariants that cannot false-positive by construction (nested sets, part-versus-whole) over tuned plausibility bands, which go stale and get muted.
5. State what a figure counts when it is not obvious. A sum over outages is not a count of people, and the label has to say so.

## Current Risks And Open Questions

- The container-to-Worker authentication path is deliberately retired: Cloudflare did not deliver a usable token or internal Worker identity, so Flask now calls only two public materialized reads and uses local-compatible fallbacks for former protected calls. Do not add a protected runtime endpoint as a container dependency without a separately designed, tested credential path.
- A private cost review establishes a threshold-crossing signal but not route attribution. The authenticated dashboard measurement supports retaining the hybrid shell; obtain route/runtime evidence before changing container idling or selecting the next public-read migration.
- Ordinary public reads should keep moving toward Worker/static/D1/R2 paths, but the right migration boundary is not yet proven.
- Archive health is deployed: stale run expiry, 30-day terminal-run retention, latest-row de-duplication, and classified archive-bin completeness. Keep monitoring the public ingestion-health endpoint and private completeness audit.
- Cursor-aware archive-summary checks are deployed and production-verified: the served summary was healthy with no cursor or coherence problem after the `v0.4.8` release. The existing payload-shape guard still handles format drift separately.
