# Storage And Retention Plan

Proposed: 2026-11-01. See the [active plan](../../PLANS.md) for current priorities and execution status.

Status: planning only; no new production scan, export, migration, retention job or deletion was performed for this plan. Priority: establish the measured storage/recovery boundary before adding Westmount or notification state. This plan preserves existing archive behavior first; event reclassification and metric corrections are the separate [identity/API plan](event-identity-api.md). Existing ADRs 0003/0005 remain in force until a reviewed implementation decision explicitly supersedes the relevant parts.

## Baseline, risks and preservation contract

- Last recorded D1 size: `3,359,739,904` bytes on the November 1 deployment probe, approximately 250 MB above October 22. That dated measurement is not a live table-size inventory or a reliable long-term forecast. 3.5 GB is the project's internal review/action trigger; 4 GB is the existing migration-action threshold. Neither is the platform failure limit. Cloudflare currently documents a 10 GB paid-plan database limit and first 5 GB included storage; confirm actual account terms and limits before executing a migration. Sources: [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [pricing](https://developers.cloudflare.com/d1/platform/pricing/).
- Observed schema: `hydro_polygon_geometries` stores both normalized GeoJSON and raw coordinates for each source version/polygon. `previous_outage_territory_bins` repeats assignment/territory and derived metric data per snapshot polygon. `resolved_events` also accumulates source-version strings. These are storage candidates, not measured attribution; indexes, other tables and free-page reuse must be measured before selecting the biggest saving.
- Old current/planned marker rows are already pruned, raw feeds live in R2, terminal ingestion runs retain 30 days, stranded runs expire after three hours, and geocode-cache rows retain 30 days. Preserve those working policies; do not claim them as new savings. Usage aggregates retain 90 days under ADR 0007.
- Important replay dependency: `outageStatsForPolygon()` currently joins marker rows for the same source version and falls back to `eventCount: 1`/an observation-time label if none remain. Raw-input retention alone does not prove that a later rebuild reproduces the original derived bin values after marker pruning. Exact existing rows and build/parser/territory versions must be preserved or reproducibly reconstructed before replacement.
- Preserve all currently supported address-history lookbacks, map geometry/detail behavior, municipal assignments, existing count units, archive windows/charts/latest/largest results, attribution, raw provenance and known gaps. ADR 0005's one-year summary guarantee is a minimum, not authorization to discard older history or shorten a longer UI/API lookback. No silent change to outage counts, spatial precision, resolution semantics or source coverage as a storage optimization.

## Phase S0 — bounded inventory and recovery rehearsal

- [ ] Refresh dated database size, row-read/write costs and growth measurements through cheap metadata/operator metrics; record timestamp, units and provenance. Observe at least a representative week for a trend when headroom permits, but do not wait past an action threshold to begin implementation. Calculate days to 3.5/4 GB using a range of growth rates, not a single guaranteed date.
- [ ] Produce a one-off bounded inventory of table/index sizes where supported, row counts/serialized lengths from a local export or sampled indexed ranges, geometry unique-digest ratio, assignment fanout, repeated text/coordinates, snapshot metadata growth and current retention effectiveness. Verify D1 support before using SQLite diagnostics such as `dbstat`/PRAGMAs; never assume local SQLite exposes identical remote facilities. Avoid recurring full-table production scans or `COUNT(*)` dashboards.
- [ ] Profile representative reads and scheduled jobs with query plans, rows read/written, response bytes and runtime: local history near a dense/sparse area, province Archive summary, current/planned map, source-detail geometry, archive cursor/backfill and raw replay. Enumerate every reader/writer of candidate tables, including Python local fallback and maintenance scripts.
- [ ] Inventory R2 source coverage by provider/source/version using manifests/indexed metadata and bounded object checks. Verify checksums and successful decompression/parsing for representative old/new inputs. Record missing objects or irreproducible derivatives as explicit gaps; do not assume archival completeness from D1 metadata alone.
- [ ] Capture a D1 recovery bookmark plus an access-controlled export and an immutable manifest of the D1 publication/build cursors and corresponding R2 object keys/hashes. A database export can include address/query data, so keep whole-database backups private, encrypted/access-restricted and outside public archive-object paths. Do not commit exports to Git.
- [ ] Restore to an isolated local/staging database and reconstruct sampled map/history/summary reads from that checkpoint plus R2. Measure restore duration and maximum recoverable/replayable interval. D1 Time Travel is a useful bounded recovery mechanism, not the sole long-term archive and not an R2/D1 cross-store transaction. Verify the account's available recovery window/bookmark before depending on it. [Time Travel documentation](https://developers.cloudflare.com/d1/reference/time-travel/).

Deliverable: dated inventory/cost worksheet, reader dependency map, recoverability report and a selected candidate with expected savings, migration peak space and 90-day growth projection. No deletion approval gate can be passed with missing source evidence or an untested restore path.

## Phase S1 — select and document the physical model

Recommended order, conditional on S0 measurements:

1. Deduplicate unchanged geometry and eliminate reconstructable duplicate coordinate text from hot D1 storage, retaining the original bytes in R2 and exact version-to-geometry references.
2. Compact repeated assignment/provenance metadata without changing any existing metric, retaining observation/assignment records and immutable legacy exports.
3. If those savings do not provide sufficient durable headroom, offload immutable older geometry/observation/assignment partitions to R2, retaining a bounded spatial/time catalog and the materialized products needed for current public reads. A lossy monthly total alone cannot replace arbitrary-radius/date history or largest/latest queries.

- [ ] Compare geometry-only dedup, combined dedup/lean assignments and cold R2 partitioning on the same local dataset. Include new index/reference overhead, CPU/reads, R2 GET/PUT amplification and rollback copies; choose the smallest change that meets the measured budget. Splitting databases is a separately measured option, not a way to ignore growth or move it beyond a dashboard threshold.
- [ ] Proposed schema boundary: immutable geometry objects with exact canonical digest plus raw-source/parser references; lean snapshot/feature→geometry links; normalized territory identity/version; lean observation→territory assignments; immutable archive partition manifests; and an atomic published archive-generation pointer. Keep published historical identities stable during physical relocation. Do not use mutable array positions or new semantic episode IDs as migration keys.
- [ ] Define versioned canonical geometry encoding, CRS, numeric precision, ring/hole/multipolygon behavior and digest algorithm. Preserve exact parsed geometry for containment/provenance. Deduplicate only verified equivalent representations; do not round/simplify geometry to get a better compression ratio. Display simplification stays a separately named derivative with measured error.
- [ ] For cold offload, choose chunk format/size and spatial/time partitioning from observed queries (compressed JSON/NDJSON with bounded decoded size is the first candidate). Store precise immutable row-level legacy representations and lineage, plus indexed bounds/time ranges and hashes. Define read fanout/CPU/byte caps, cross-partition merging and pagination before moving anything. R2 is object storage, not a relational query engine; never scan the bucket on a public request.
- [ ] Keep current feeds and recent working sets hot; choose any hot-age cutoff from query measurements rather than silently declaring old history unavailable. Public full-coverage reads must reach the cold tier where required. For a date/radius that exceeds safe fanout, return an honest bounded-query response rather than a partial result labelled complete; preserve existing supported UI behavior through suitable materialization/indexing before cutover.
- [ ] Proposed acceptance budget to confirm after S0: post-migration D1 at or below 3.0 GB and at least 90 projected days before 3.5 GB at a conservative measured growth rate, with no unexplained archive regression. If geometry-only work misses that budget, continue to measured offload or choose a documented alternative; do not close retention planning on a small one-time shrink. Write concrete request-latency, R2-fanout, row-read/write and monthly-cost budgets before implementation, comparing with the recorded baseline.
- [ ] Record the selected physical model, retention exceptions, reclaim strategy and deletion conditions in a successor/amendment to ADR 0005 during implementation. A plan is not an accepted architecture decision. Update `docs/architecture.md`, operations and public disclosure where behavior/storage boundaries actually change.

## Retention matrix — preserve sources, bound operational/private state

| Data class | Proposed policy / existing boundary | Removal gate |
| --- | --- | --- |
| Public source raw payloads/DAI inputs and required source manifests | Preserve in R2 with checksums/provenance; no automatic expiry introduced. Respect documented source-specific restrictions. Dedup exact content only while retaining every fetch/version reference needed for replay. | Separate documented legal/source policy or verified redundant object with no live/reference/backup dependency; not a D1-pressure shortcut. |
| Geometry, archive observations and territory assignments | Preserve information for all supported history windows; change physical location/encoding after exact parity. Never reduce to a count-only rollup when individual/spatial reads still need the evidence. | Durable verified replacement plus replay/parity, successor ADR, rollback manifest and explicit production cleanup authorization. |
| Snapshot metadata, provider identity/gaps and public historical-ID mappings | Retain logical provenance; older detailed membership may be partitioned, but published IDs/source lookups remain resolvable. | No dangling geometry/raw/identity/summary references; no silent history loss. |
| Current/planned feed rows | Existing latest-version policy continues; pin generations needed by active readers/builds and prove raw replay before replacing the existing cleanup implementation. | Complete committed successor, unpinned old generation and successful archive/provenance processing. |
| Archive/context summaries and display assets | Rebuildable immutable generations; retain active plus rollback generations until the retention/reader-pin window ends. | No published manifest or cursor references the candidate; rebuild evidence exists. |
| Ingestion runs/geocode cache/usage evidence | Preserve existing 30-day terminal runs, 3-hour run expiry, 30-day geocode cache, 90-day aggregate usage policy. Private address/query/match tables require a separate inventory/purpose decision; no inferred indefinite retention. | Purpose-specific bounded cleanup and tests, without deleting source observations or conflating private service data with public archive data. |
| Future notification locations/subscriptions/outbox | Follow the notification plan's explicit opt-in, deletion/lease/expiry policy; never store private subscription data in permanent raw-source archives. | Owner deletion, lease/endpoint expiry and defined short delivery-state retention; do not reuse public-history retention. |
| Migration exports/checkpoints/quarantine | Private, dated and pinned only for the agreed recovery window. Proposed old-generation/export hold: at least 14 days after stable cutover, subject to private-data backup rules; then deliberate eligible cleanup. | Restore/parity evidence, published retention duration and no active migration/reader pins. R2 garbage collection remains off until the reference audit works. |

## Phase S2 — replayable build and safe publication

- [ ] Create additive schema and a resumable offline/maintenance builder with an immutable job specification, source high-water mark, fixed parser/territory/build versions and indexed keyset cursor. No giant one-transaction rewrite. Bound rows, bytes, elapsed time and costs per batch; checkpoint only after durable writes. Repeating a batch must not increase event/observation counts or duplicate membership rows.
- [ ] Preserve exact original derived rows into checksummed immutable chunks before transforming them, especially where old marker rows are gone or a legacy calculation cannot be reproduced from available inputs. Rebuild-from-raw and preserving legacy materialization are separate paths; compare them and document differences rather than silently choosing a new number.
- [ ] Build new geometry references/partitions/manifests off the request path. R2 upload → verify hash/count/read/decode → commit D1 catalog/staged rows → atomically advance one published generation only after every component is complete. R2 consistency does not provide an atomic transaction with D1 or CDN caches; immutable object names and a single D1 publication boundary are still required. [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).
- [ ] Keep old readers/writers operational during bulk build. Capture a starting watermark, then replay the ingest tail into the new store or dual-write through an idempotent adapter. At final cutover acquire a bounded publication lease, drain/record the tail and atomically publish compatible cursors/read configuration. Raw collection can continue during a short normalized-publication pause; never discard versions received during migration.
- [ ] Rebase numeric/compound archive cursors through explicit old→new mappings, not a count or lexicographic guess. Check no skipped/duplicated polygon, unassigned/outside-territory classifications and summary source-cursor coherence. Pinned in-flight readers must see one generation, not old counts paired with new geometry.
- [ ] Prove peak-capacity safety before starting: existing tables + shadow references/objects/indexes + temporary rebuild/export overhead + expected ingest growth + rollback hold. A same-database table rebuild may temporarily use far more space than the final layout. If it exceeds headroom/budgets, use a staged offload or separately authorized replacement database and binding cutover; do not run the old large-table-copy strategy blindly.

## Phase S3 — parity, cleanup and measured reclamation

- [ ] Compare all legacy/staged row counts by provider/source/time partition, geometry checksums/equivalence, assignment types, nulls, retained versions/gaps and raw-object resolvability. Counts alone are insufficient: compare deterministic row hashes and selected full records. No unmatched rows or broken references outside an explicitly recorded pre-existing gap.
- [ ] Compare actual query results for dense/sparse/border/hole/multipolygon addresses and all existing UI time/radius windows, municipal/province summaries, largest/latest rows and raw provenance. Preserve exact values/ordering under the legacy metric definition; do not “fix” unit/grouping errors in the storage migration. Carry known semantic limitations forward with labels until the separately reviewed identity correction.
- [ ] Run fault/restart checks: partial R2 upload, failed D1 batch, missing/corrupt chunk, stale catalog, lease expiry, ingest during build/cutover, repeated tail replay and worker rollback. A failed read is unavailable/stale, never an empty archive or a forced request-time rebuild of the full dataset.
- [ ] Canary/shadow read comparisons first, then explicitly authorized reader cutover. Observe at least seven complete days of ingestion/summary/ordinary reads, plus the agreed 14-day rollback hold before removing old payloads. Avoid daily full production audits: do comprehensive checks locally/staging and bounded production canaries with full checkpoint manifests.
- [ ] Cleanup is a distinct reviewed step with exact eligible IDs/ranges, retained replacement manifests/checksums, estimated savings and restore plan. Default to dry-run. Remove only verified unpinned derived duplicates in bounded batches; no raw-source, history or private-data policy expansion hidden in a generic cleanup function.
- [ ] Verify actual D1 size/free-page reuse and rows read/written after cleanup. A DELETE count is not evidence that billed/physical database size decreased. Test supported reclamation behavior on staging; do not assume `VACUUM` works remotely. Use a tested bounded rebuild/replacement-db path if needed, with account-specific limits and migration cost reviewed first. Never issue an unbounded production delete/rebuild to force a size graph downward.
- [ ] Add cheap weekly size/growth forecasts and threshold warnings to existing operations, with monthly cost/recovery checks. Monitor archive completeness/cursors and raw-replay checks separately. A healthy ingestion endpoint does not establish that archival reconstruction or backup restore works.

Recovery and rollback: before cleanup, revert the reader-generation pointer and compatible writer configuration, then replay any captured tail. After cleanup, restore the immutable legacy partitions/new-store checkpoint and rehearse reconstruction in isolation; use a whole-D1 Time Travel restore only with a plan for writes since the bookmark, source replay and private deletion/expiry records. Do not resurrect deleted notification/user data through a bulk restore; retain/reapply deletion tombstones under the private-data policy. A rollback must preserve both the old public information and post-checkpoint observations, not merely make the homepage load.

Implementation slices: S0 inventory/restore tooling and evidence → selected-model ADR/fixtures → additive storage and resumable builder → shadow readers/tail parity → explicitly authorized cutover → separately authorized eligible cleanup/reclamation. Relevant files include migrations, `src/worker.js` storage/ingest/backfill paths, `src/municipal-archive.js`, `src/archive-summary.js`, `src/durable-read-handlers.js`, Python fallback readers and maintenance tooling. New helpers remain under their runtime boundary; choose migration numbers from the implementation head.

Verification: real local/staging D1/R2 integration tests for publication/replay/deletion and fault recovery; Python/Node parity fixtures and archive coherence tests; full pre-commit, Python, Node and Playwright suites for reader/service changes, plus actual desktop/mobile Archive/history checks. Run Wrangler dry-run and representative migration/restore drills before any authorized production action. Exit requires preserved query/provenance behavior, measured reclaimed/headroom budget, bounded ongoing growth/cost, functioning recovery, and no automatic destructive policy beyond the accepted ADR.
