# Event Identity And API Contracts Plan

Proposed: 2026-11-01. See the [active plan](../../PLANS.md) for current priorities and execution status.

Status: planning only. No published API is made stable by this document, and no event IDs/counts are migrated here. Follow the [storage preservation plan](storage-retention.md): first freeze an inventory of existing references/semantics, preserve/replay legacy data, then change interpretation through a separately versioned model. An internal identity contract can be developed alongside storage; a public stability promise waits for evidence, operational limits and the existing `0.5.x` entry gates.

## Observed implementation and the decisions it cannot support yet

- HQ live rows currently use `bis:<source_version>:<record_index>` / `aip:<source_version>:<record_index>`. These locate a row in one source version; they do not identify one physical outage across snapshots. The planned feed exposes a `notice_id` field, but its uniqueness, reuse and schedule-revision lifecycle still need validation.
- `resolved_events` is upserted while ingesting current/planned sightings. Its name does not establish actual restoration. The current Worker grouping key combines kind, municipality, centroid rounded to three decimals, interruption type and a minute-level start-time string; estimated restoration can be stored in generic `end_time`. `record_count` increments on every upsert, and comma-separated `source_versions` carries provenance. These are legacy heuristic groupings, not proven utility incident identity or replay-safe counters.
- Python builds a similar key using `round()` and default float stringification; Worker uses fixed-width `toFixed(3)`. Equivalent coordinates can therefore serialize differently. Also audit planned-time mapping: Python's initial generic `end_time` reads column 2, while the Worker planned branch reads column 3. These are code-review observations requiring focused characterization tests, not claims that a particular live record/user answer was wrong.
- Existing map geometry/render grouping is another identity (including a coarser centroid-based previous-layer grouping), and municipal bins identify a polygon sighting/territory assignment. Do not treat every UI render group, archive bin, retained sighting, notification candidate and source incident as interchangeable.
- Westmount provides network-block identity/status; no upstream incident ID was established. Source timestamps and the client-count meaning remain under its separate validation gate. Saved-area notifications require stable correlation/dedup before they can safely alert across source updates.

## Shared vocabulary and identity types

| Concept | Proposed identity and meaning | Explicit non-guarantee |
| --- | --- | --- |
| Provider/source definition | Stable provider key plus source/layer definition version and identity epoch where upstream IDs can be reused. | A municipality name is not a distributor or exclusive service territory. |
| Raw snapshot/publication | Provider/source + immutable publication manifest, containing upstream version/identity epoch and content digest/revision; separate fetch-attempt metadata. Exact blobs deduplicate by digest, while distinct claimed publications retain separate references. Preserve different bytes even if the upstream reuses a version label. | A source version string or successful fetch does not prove current/comprehensive upstream data. |
| Observation | Opaque immutable ID bound to a raw snapshot and exact record locator. A locator may use an index **inside those immutable bytes**; parser output has a separate revision. | This does not identify a physical outage across snapshots; a parser replay is not a new sighting. |
| Source entity | Provider/source/epoch + verified persistent native ID (e.g. Westmount block or validated planned notice). | Block/notice existence is not an outage incident; a removed/reused ID is not the same entity automatically. |
| Inferred episode | Persisted opaque ID plus derivation version and linked observations describing a conservatively correlated period/entity state. | It is not an official utility incident ID; ambiguous merge/split/reopening remains explicit. |
| Geometry | Exact canonical geometry digest/version, separate from immutable raw/source geometry IDs and display derivatives. | Same geometry does not mean same incident; changing geometry does not by itself mean a new incident. |
| Published dataset generation | Immutable manifest of provider/product component cursors and parser/model/territory versions; readers pin one generation. | Multiple upstream resources need not have been captured at one atomic instant; include their capture ranges. |

Proposed public IDs are opaque and provider-qualified in the resource envelope; no raw address, coordinate or heuristic centroid/time string in an identifier. Use a persisted mapping, not a recalculated mutable semantic hash, for episode/public identity. Internal hashes still require versioned canonicalization and collision/multiplicity handling. Preserve raw source IDs separately as qualified provenance only when suitable for public release.

## Phase I0 — characterize and define the identity contract

- [ ] Inventory all current IDs/keys and their consumers: D1/SQLite tables, archive cursors/summaries, map selection/render keys, URLs, browser comparison/local storage, raw references, fakes and tests. Capture existing behavior before correcting it. Map an old reference to a legacy representation even where it cannot map uniquely to a newly inferred episode.
- [ ] Build a representative, provenance-labelled replay corpus: quiet and storm periods, row reorder, unchanged repeat/version changes, edited customer counts/ETAs/start times, missing coordinates, null/unrecognized codes, duplicate indistinguishable rows, overlapping events, lost/partial snapshots, planned revisions/cancellations and event disappearance/reappearance. Include verified real source examples; synthetic cases exercise faults but do not establish upstream meanings.
- [ ] Establish observation uniqueness and replay rules. Reprocessing the same `(raw_snapshot, record_locator)` updates a parser revision/materialization, never `record_count` or a new first-seen time. A repeated fetch/retry of the same accepted publication records successful validation without creating duplicate sightings. A genuinely new source publication may reference the same deduplicated bytes while retaining its own observation/publication provenance; define that distinction consistently in the metric contract. If equivalent rows appear twice in one snapshot, preserve raw multiplicity/locators and mark ambiguity; do not invent two independently verified incidents.
- [ ] Specify cross-language canonicalization in fixture vectors: missing/null versus zero, numeric/string native IDs, Unicode, decimal serialization, date/timezone/DST, raw version/digest handling and input ordering. Choose one contract with executable shared JSON fixtures; do not expect Python rounding and JavaScript fixed-decimal behavior to align by accident.
- [ ] Validate source-native IDs before using them across snapshots. HQ notice ID may qualify after checking reuse/revision semantics; do not assume a column position or a KML polygon index is an incident ID. Westmount block IDs need source epochs and split/merge handling. Provider identity is mandatory; never merge across distributors because locations/times happen to match.

Exit: an explicit model/identity specification, characterized legacy differences and a replay corpus. Write an identity ADR during implementation before migration; source ambiguity is recorded, not concealed with confident UUIDs.

## Phase I1 — conservative correlation and chronology

- [ ] Separate authoritative native linkage from inferred linkage. Store method, derivation version, evidence and uncertainty/ambiguity reason; avoid presenting a numerical “confidence score” as calibrated truth unless validated. Native keys still require provider/source/epoch and reuse rules.
- [ ] Proposed HQ policy: use validated native linkage when available; otherwise correlate consecutive complete observations conservatively using reported start, supported kind/status, geometry overlap/proximity and other verified source evidence. Define tolerances only after corpus evaluation, with negative examples of nearby simultaneous outages. Do not use exact ETA, customer count, a rounded centroid or mutable raw row index as the sole identity criterion.
- [ ] Persist inferred episode IDs and a versioned observation→episode relation. Changes to a matching rule rebuild a new model generation with comparison/mapping evidence; they do not overwrite raw history or silently mutate already public IDs. Unknown ties, multi-candidate merges/splits and continuity gaps remain ambiguous. Keep relationship records (`supersedes`, `split_from`, `merged_from`) where justified; never pretend every legacy group maps one-to-one.
- [ ] For Westmount, derive block-state episodes as specified in its plan, not cross-block utility incidents. Do not infer an outage from a block's existence, or count a change between planned/ongoing state as a second independently verified physical incident. For alerts, one ongoing correlated episode should not re-alert on ETA/count/polygon edits; an uncertain reopen after a collection gap establishes a cautious baseline rather than a confident new-start push.
- [ ] Use separate fields for `reported_start_at`, `estimated_restore_at`, `reported_end_at`, `first_observed_at`, `last_observed_at`, and observed restoration bounds. Source-local/ambiguous values retain raw text and an unknown/qualified parsed value; do not treat UTC formatting as timezone verification. `end_time`/last sighting/estimated restore never becomes confirmed restoration just because it is non-null.
- [ ] Define statuses and closure evidence: ongoing, planned, no longer observed, explicitly reported resolved, and unknown are distinct. Complete-feed disappearance can bound a last observation but is not necessarily restored service. Source failures, partial pages, missing geometry or unknown codes do not close episodes or create all-clear alerts. Account for left/right censoring and gaps; do not calculate exact outage durations/customer-hours from unsupported bounds.
- [ ] Define each metric with a unit and inclusion rule: observations, distinct source features/blocks, inferred episodes, confirmed native incidents (only if available), per-observation affected customers, summed episode-associated counts and distinct customers. Unknown is nullable, not zero. Summing affected counts across times/providers is not distinct people/service points; overlap can make block/customer sums unsafe even within one source.

Exit: replay demonstrates stable episode linkage under benign changes, replay-idempotent observation counts, retained ambiguity in adversarial cases and no fabricated resolution/count precision. Notification-specific dedup consumes this internal contract; it must not create a separate incompatible outage identity model.

## Phase I2 — additive migration and compatibility

- [ ] Add source/snapshot/observation, parsed-revision, entity/episode, membership/lineage, geometry-reference and coverage-gap tables or equivalents selected with the storage plan. Normalize provenance membership rather than an unbounded CSV. Index provider/time/bounds and membership/uniqueness for actual bounded queries; measure growth rather than keeping an unlimited second copy in D1.
- [ ] Build from retained immutable input/manifests and preserved legacy exports. Stage revised groupings/counts in a separate model generation; compare differences against legacy summaries and manually inspect ambiguous examples. Physical compaction parity and semantic correction acceptance are different reports/releases. No one-shot rewrite of legacy keys or retroactive claim that collection was complete.
- [ ] Maintain legacy-ID aliases/lookup records and versioned raw lineage. Keep first-party UI/local references working, with explicit ambiguous/unavailable behavior where a mapping is not unique. Do not rewrite published stable IDs later just because the parser/correlation improves; serve a revision/status/relationship or a documented tombstone with safe links.
- [ ] Recompute stored summaries under a named model/metric version and source cursor. Publish only coherent complete generations; never mix legacy polygon counts with revised episode counts in one comparison/chart/headline. Update labels/limits before exposing new semantics. Historical notification backfill stays disabled during a rebuild/cutover.
- [ ] Retain Python fallback/Worker behavior parity through shared fixture vectors and service-fake contract tests. The existing unstable routes can use adapters; do not destabilize their first-party callers as an incidental cost of preparing a new stable route.

## Phase A0 — freeze the minimal public contract

The internal provider/identity contract is useful immediately to future implementation. The **external** v1 API remains a later gated release: successful source observation ≠ validated episode history ≠ stable third-party contract. Preserve ADR 0004 and the current `unstable` labels until a replacement decision/spec/tests are accepted.

Proposed first version: bounded provider/coverage metadata, current nearby observations and retained historical **observations** with explicit units/provenance. Inferred episodes may be added only after their identity/chronology gates pass; do not expose today's `resolved_events` as confirmed resolved incidents under a new URL. Source licensing/redistribution boundaries apply even if a browser page already shows a field.

| Proposed route (not implemented) | Contract boundary |
| --- | --- |
| `GET /api/v1/providers` | Public providers, source/coverage capabilities, collection start, current availability and attribution links; no operational secrets or subscriber counts. Only enabled/validated coverage is advertised. |
| `POST /api/v1/nearby` | Read-only structured query for a provider and center/radius; returns current/planned observations with separate source status. Body coordinates avoid putting locations into API URLs; redact bodies/query values from operational logs. No stored search/profile as a side effect. |
| `POST /api/v1/history` | Bounded retained-observation query with explicit time basis/range and the same spatial contract. Repeated sightings are labelled as observations, not distinct outages. Cold archive lookups must satisfy the storage plan's completeness/fanout bounds. |
| `GET /api/v1/observations/{opaque_id}` | Immutable observation identity plus a qualified parsed revision, reported/observed times, provider/source and permitted provenance/geometry references. No unrestricted raw object URL. |
| `GET /api/v1/geometries/{opaque_id}` | Bounded permitted geometry with CRS, precision and source/derivative version; immutable representations use matching cache validators. No arbitrary upstream URL proxy. |
| `GET /api/v1/episodes/{opaque_id}` | Later candidate, only once inferred/native identity and correction/tombstone behavior are accepted. Representation identifies block episode versus inferred outage versus verified native incident. |

Do not expose private saved areas, notification endpoints/keys, addresses/search history, operation tokens, raw disclosure files or unrestricted raw-feed records through this public surface. Private notification management APIs have separate ownership/CSRF/retention contracts and are not a public API-key/account feature.

- [ ] Author an OpenAPI 3.1-compatible document and versioned JSON Schemas with concrete normal/empty/stale/unknown/error examples; choose the exact specification/tool versions at implementation time and validate their compatibility. [OpenAPI reference](https://spec.openapis.org/oas/v3.1.1.html). Keep machine-readable semantics, human docs, fixtures and actual responses in agreement.
- [ ] Require an explicit provider and spatial parameters for query routes initially; no implicit province-wide scan/all-provider aggregate. Proposed limits: radius 100–10,000 m, page size default 100/max 500, history range at most 31 days/request and mandatory UTC or offset-qualified `[from,to)` bounds. These are proposed v1 query limits, not deletion/retention limits or changes to existing UI lookbacks. Fix bounds and operational cost evidence before announcing stability.
- [ ] Define history time basis (default `observed_at`, reported start only when explicitly requested/supported), WGS84 `[longitude,latitude]`, metres, source versus display geometry, containment/intersection versus centroid distance and deterministic result ordering. Validate nonfinite/out-of-range values, reversed dates, unknown fields and unsupported combinations; no silent radius/date clipping that changes the question.
- [ ] Select an envelope with `api_version`, `model_version`, `generation`, provider/source, capture range, last successful validation, source-reported update (nullable), coverage/known gaps, record kind/count unit, data and page metadata. `returned_count` counts this page only; no implied distinct incidents/customers or unbounded total-count query. Pagination completeness, source validation completeness and historical collection continuity are different facts.
- [ ] A successful request does not reset `checked_at`/source age. Encode available, valid-empty, not-covered/not-yet-collected, stale, partial and unavailable explicitly. For live queries, default to a 503 problem response when no usable sufficiently fresh dataset can answer; optional explicit `allow_stale` can return last-good data with age/warnings. A valid complete source with no matches returns 200/empty. Historical known gaps appear in coverage even when the retained result page is complete. Never return fabricated empty data on a failed R2/D1 read.
- [ ] Freeze one consistent set of error codes: malformed/unsupported requests 400 (or documented 422 for an otherwise valid query exceeding the supported query budget), unknown public resource 404, tombstoned resource 410 where appropriate, cursor invalid 400/expired generation 409, quota 429 with retry guidance and data/service unavailable 503. Use bounded [RFC 9457 problem details](https://www.rfc-editor.org/rfc/rfc9457.html); no stack traces, SQL, object keys, private endpoints or reflected sensitive query text.

Example shape to refine in the spec (illustrative, not an existing response or a stable schema):

```json
{
  "api_version": "1",
  "model_version": "observations-1",
  "generation": "opaque-generation",
  "provider": "hydro_quebec",
  "source_state": {"status": "available", "checked_at": "2026-11-01T18:00:00Z", "reported_updated_at": null},
  "coverage": {"collection_start": "2026-01-01T00:00:00Z", "continuity": "known_gaps", "gap_count": 1},
  "record_kind": "observation",
  "count_unit": "observations",
  "returned_count": 0,
  "data": [],
  "page": {"has_more": false, "next_cursor": null}
}
```

The example's timestamps and gap values are illustrative, not assertions of actual production collection completeness. The real contract must provide bounded gap/detail links and source-specific dates.

## Phase A1 — pagination, consistency, caching and abuse budgets

- [ ] Use keyset pagination with an opaque authenticated cursor bound to route/filter hash, provider, time basis/range, generation/model, sort tuple and expiry. Encrypt or server-reference sensitive filter values; a signed plaintext coordinate-bearing cursor can still leak location. Stable order includes an immutable tie-breaker; out-of-order/backfilled observations never duplicate/skip records within a pinned traversal.
- [ ] Proposed cursor/generation lease: 24 hours for an active traversal, with old-generation retention/readability for at least that lease plus an explicit safety margin. Coordinate storage cleanup with reader pins and the 14-day migration rollback hold; “immutable generation” is not a promise of infinite snapshot retention. Expired generations produce the documented restart response, not a cursor silently applied to today's data.
- [ ] Pin compatible component manifests: HQ current/planned/geometry and archive materializations may update independently, and provider snapshots are not globally atomic. Include each component's source version/capture range and completeness. Do not silently attach geometry from a different version or let live data changes alter page two of a historical result set.
- [ ] Version parsing/derivation and freeze what an observation representation means. Raw observation identity stays immutable; a corrected parsed revision can be a new explicitly versioned representation with validators. State the default revision-selection/correction policy; keep old model versions available through the promised transition window rather than changing a field's meaning invisibly.
- [ ] Cache public provider/immutable geometry/observation representations by their actual generation/model/revision and ETag. Nearby/history POST responses containing requested locations are `no-store` initially; any internal materialization cache has a bounded keyed contract and does not log/store a user search profile. Conditional response validators must cover all semantic versions, provider, filters and freshness/coverage fields that affect the response.
- [ ] Public v1 initially needs no subscriber account or marketing API key. Before exposure, set numeric request/query/range/fanout/response-byte/concurrency and global monthly cost budgets using load tests. Rate controls must work at the edge or Worker under the account's actual rule/binding limits; the existing autocomplete/usage rule does not cover these routes automatically. If sufficient abuse control is unavailable, hold public activation or narrow the surface instead of exposing expensive reads unchecked.
- [ ] Define CORS explicitly for public read-only consumption, with no credentials; private notification APIs remain same-origin and credentialed. Test OPTIONS, body limits, unsupported methods and allowed response headers. Origin/CORS is not authorization or a rate limiter. Do not enable arbitrary SQL, raw-object retrieval, bulk background exports, provider URLs or uncapped geometry expansion.
- [ ] Publish freshness expectations from source cadence plus processing/materialization, without a contractual instantaneous-delivery SLA. Provide examples for a complete empty response versus stale/unavailable/coverage gaps, retry/caching guidance, pagination restart and correct count interpretation.

## Phase A2 — compatibility, validation and release

- [ ] First-party clients exercise internal/unstable adapters before public stability is declared. Do not rename `/api/durable/hydro` to mean all providers or silently change its count unit. Existing stable page URLs/search parameters remain compatible; stable v1 routes are additive. Update `docs/api-posture.md`, `/llms.txt`, About/provenance and operations together when stability actually changes.
- [ ] Proposed v1 policy: adding a genuinely optional field or a new provider/capability must not break conforming clients; clients ignore unknown fields and handle documented unknown status values. Removing/renaming fields, tightening established limits, changing units/time basis/ID semantics, new required fields or altered nullability is a breaking change requiring a new major contract or an explicitly agreed compatibility mechanism. Publish a concrete deprecation window before v1 launch (proposed minimum 90 days), with version-specific changelog/examples and migration guidance. No silent withdrawal of existing published IDs/history because a storage tier moves.
- [ ] Ship raw/parsed/episode correction procedures: preserve the evidence, create a new parser/model revision, record reason and affected resources, compare/canary, update generation/validators and disclose material interpretation changes. Episode merges/splits retain resolvable old IDs and qualified relationships/tombstones; notification consumers do not turn a parser correction into a new outage alert.
- [ ] Tests validate actual Worker/Python serialized responses against the spec, not only constants or hand-written examples. Cross-language fixture vectors cover key formatting/nulls/date ambiguity and planned times. Add repeated identical-input replay, reordered rows, jittered geometry/ETAs, native-ID reuse, mixed providers, duplicate ambiguous rows, gap/reopening, split/merge and no-confirmed-resolution cases. `record_count` is the count of unique included observations under the contract, not the number of times a job retried.
- [ ] Integration tests cover pagination with equal times, concurrent new generations, cursor tampering/expiry, hot/cold archive parity, missing R2 object, partial source, stale source, wrong provider/geometry, schema/model upgrades, rate caps, errors/CORS/cache validators and forbidden private fields. Use local/staging persistence for publication/transaction behavior and a consumer smoke test against the actual staged routes.
- [ ] Run relevant Node/Python/contract checks, full pre-commit and Playwright when service/routes/templates/browser consumers change; inspect desktop/mobile map/search/history/provider labels and totals. Do not publish a machine-readable contract on a production path before its served responses and operational limits pass the same tests.
- [ ] Roll out additive storage/identity adapters, then shadow model comparisons, then first-party consumers, then an explicitly authorized staged/public v1 release. Record a successor ADR for public stability only at the accepted contract boundary. Rollback keeps stable v1 responses/IDs compatible where possible; return a documented availability error during incidents rather than falling back to incompatible legacy semantics.

Implementation sequence: legacy characterization + shared vocabulary/schema vectors → observation identity/replay fixes + lineage/aliases → conservative episode model + revised metric labels → versioned OpenAPI/query/cursor/error specification → bounded Worker endpoints/load/privacy tests → first-party/staged validation → separately authorized public stability. Storage compaction can ship first without waiting for semantic reclassification; notifications wait on sufficient identity/health guarantees, and Westmount can share the provider/source model without pretending block status equals an incident.

Definition of done: observation and episode identities/units are unambiguous and reproducible; retries never inflate counts; ETAs are not advertised as confirmed ends; gaps/uncertainty survive migration; old references remain explainable; complete pinned queries survive hot/cold relocation; actual responses match a versioned schema; operational/privacy/cost bounds and compatibility policy are enforceable. No source/utility certification or unique-household reliability claim is introduced.
