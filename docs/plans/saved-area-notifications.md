# Saved-Area Web Notifications Plan

Proposed: 2026-11-01. See the [active plan](../../PLANS.md) for current priorities and execution status.

Status: detailed planning, not implemented or scheduled. No subscription, notification, new cloud resource, tracking change or deployment is authorized by this document. This replaces the vague notification-backlog entry with a concrete proposal; readiness/privacy/cost gates still apply. The user has requested this plan, which establishes interest but does not establish broader adoption demand or production readiness.

## Product outcome and first-release boundaries

Save a few locations from the existing address/map flow and optionally receive a browser notification when a new outage is observed nearby. Keep the map and sheet as the primary interface; add a small saved-areas list and per-area notification controls rather than a new dashboard or navigation redesign.

Proposed defaults, subject to validation before implementation:

- Up to five saved areas per browser installation. Store a chosen center and one of the existing 1/2/5/10 km radii (2 km default for a typed address), a local display label, language and source-coverage choices. Show the radius and coverage before saving; a nearby alert is not proof that the selected residence lost power.
- Saved areas work **locally without an account or notification permission**. Labels/typed addresses stay on the device. No automatic conversion of the current six-item comparison tray or search history into saved/server-monitored locations.
- Explicit notification opt-in uploads only the monitoring geometry/radius, provider preferences, minimal device-management credential and push-subscription material. Explain that these data must remain on our server to match outages while the site is closed. Saving locally and enabling remote monitoring are separate actions.
- First alert type: newly observed ongoing outage near an enabled area. Start with Hydro-Québec, whose production collection already exists; Westmount is eligible only after its own source/semantics/public-launch gates pass. Do not make this feature depend on Westmount implementation, or silently enroll a newly supported provider into an existing area's alerts.
- Planned-interruption notices/reminders, restoration messages and material restoration-estimate changes are later, separately enabled alert types. No email/SMS, accounts, cross-device sync, background location tracking, social notices, historical backfill alerts or emergency/guaranteed-delivery promise in the first release.
- Default notification text is generic enough for a lock screen: an outage was observed near a saved area; open pannes.ca for the details and checked time. Do not include an address, local label, precise coordinate or assertion that power is off/on at home. Users may later opt into a more descriptive label after seeing a privacy preview.

## Baseline and platform constraints

Observed in the repository: `app/static/search.js` registers the service worker and stores a browser-local comparison tray. `app/static/service-worker.js` currently handles installation/activation and an offline navigation fallback only. A manifest already exists at `app/static/manifest.webmanifest`, linked from the shell with standalone/scope/installability tests. There is no saved-area subscription model, permission flow, push handler, push sender or notification route.

- Implement standards-based Push API/Web Notifications with a service worker, VAPID and encrypted payloads. Browser push services relay delivery; “first-party feature” does not mean no third-party transport. Select a maintained Worker-compatible Web Push implementation after a small compatibility/dependency audit; do not implement message encryption/signing from scratch or wake Flask to send pushes. Reference: [W3C Push API](https://www.w3.org/TR/push-api/) (currently a working draft) and [Apple Web Push documentation](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).
- Permission is requested only after the user deliberately enables alerts. Show coverage, upload disclosure and platform requirements first. No permission prompt on arrival, saving an area, or reopening a denied permission. Use capability detection and a usable local-only state for unsupported/denied browsers.
- For iOS/iPadOS, plan and test the Home Screen web-app path and permission request from a direct user gesture; an ordinary browser tab is not an equivalent delivery test. Revalidate current browser/OS support at implementation time rather than promising support from user-agent strings. [WebKit guidance](https://webkit.org/blog/13878/).
- OS/browser permission, Focus settings, offline devices, push expiry and upstream collection cadence affect delivery. Existing HQ polling is about every 15 minutes; a faster push dispatcher cannot make source observations instantaneous. Show “observed nearby,” not “just started,” and distinguish provider acceptance from actual device display.
- Do not rely on browser background timers, Background Sync availability, an open tab or silent push as a general heartbeat. Each real push must produce a visible notification; use `userVisibleOnly` and appropriate visible handling. Do not use silent messages for analytics or background location collection.

## Phase 0 — decisions, privacy and source-readiness gate

- [ ] Confirm the bounded product defaults above and document alert wording, coverage, frequency caps, radius choices, first-release browser matrix and accountless/device-local limitations. Initial limits: five areas/device, one push subscription per browser installation, one grouped new-outage notification/device/provider per 15 minutes and a provisional maximum 12 ordinary alerts/device/day. Preserve suppressed events as a bounded summary for the next eligible alert, not an unlimited catch-up backlog. Tune during opt-in beta; caps are not permission to send irrelevant pushes.
- [ ] Choose source/event semantics: first-release matching must have reproducible provider-qualified logical event identity and complete published generations. HQ `source_version + record_index` alone is unstable across refreshes. Identify supported upstream IDs or validate a conservative correlation strategy using retained raw payloads and real examples; changing row order, source versions or polygon jitter must not cause a new alert every poll. If reliable correlation cannot be established, narrow the release behavior instead of claiming event-level alerts.
- [ ] Define initial baseline behavior. Enabling an area, changing its radius/providers, re-enabling after a pause or recovering from a long collection gap establishes a new baseline without retroactive “new outage” pushes. Show existing matches in the sheet. A user-triggered test notification is clearly labelled as a test.
- [ ] Document a service-data privacy/retention decision in a new ADR during implementation. Keep ADR 0007's identifier-free analytics unchanged: operational notification subscriptions necessarily contain identifiers and monitoring coordinates, collected only for this explicitly requested service. Update architecture, About/privacy and route documentation with purpose, fields, access/deletion, push transport, expiry and logging limits. GPC/DNT continues to suppress usage evidence; an explicit notification opt-in is not analytics consent.
- [ ] Establish a bounded beta/storage/delivery budget before creating resources. Current D1 headroom must be reviewed alongside Westmount/archive plans. Do not repurpose public archives or anonymous usage tables as subscription storage. No third-party notification-marketing SDK.

Exit: privacy/product/identity choices and measurable limits recorded; reliable current-source generations and event matching available; no unresolved sensitive-data or cost dependency hidden behind a public opt-in button.

## Phase 1 — browser-local saved areas and controls

- [ ] Add a versioned local saved-area store (IndexedDB preferred for structured data) and a small module under `app/static/`; support create, rename, change radius, reorder, pause alerts and delete. Generate random local IDs. Validate lat/lon/radius/length/count and render labels as text; handle storage unavailable/full, migrations, corruption and local reset gracefully.
- [ ] Add “Save this area” to an existing address answer/map-selection flow and an accessible saved-areas list in the sheet. Reopening a saved area restores center/radius and runs the normal search/read path. Never save a moving/geolocation watch; browser location remains a deliberate one-time selection.
- [ ] Saving requires no backend write. Keep the comparison tray behavior intact and offer only an explicit user-chosen copy into saved areas. Do not share local labels with analytics or put coordinates/addresses into notification management URLs.
- [ ] Show per-area state: local only, notifications off, setup required, enabled, paused, source unavailable/stale, expired subscription or blocked browser permission. Keep browser permission distinct from server enrollment; “granted” alone does not mean delivery is configured.
- [ ] Present accountless limits clearly: areas belong to this browser installation, do not sync to another device, and may be lost when site data is cleared. A Home Screen installation may have a different storage/permission context; verify the actual iOS flow and avoid promising that a browser-tab save automatically appears in the installed app.

Exit: saved areas are useful independently of push and pass desktop/mobile accessibility, persistence, reload/navigation and failure-state checks.

## Phase 2 — private enrollment and subscription lifecycle

Proposed backend: new notification-specific Worker routes backed by dedicated D1 tables and Worker secrets. These routes are private to a browser enrollment, not public exports and not protected by the operator token. Never expose an operational token to browser code.

- [ ] On explicit enable, register/use the existing service worker, obtain permission and a browser push subscription with a public VAPID key, then atomically enroll selected areas server-side. If setup fails, display the actual partial state and allow retry; do not claim success or repeatedly request permission. If the server write fails after browser subscription, reconcile/undo the unused subscription where practical.
- [ ] Use an installation-scoped high-entropy credential in a Secure, HttpOnly, same-origin SameSite cookie, with a hashed verifier server-side; require Origin checks/CSRF protection and appropriate fetch metadata on mutations. A random public area/subscription ID is not authorization. Bind every list/read/update/delete/test request to the enrollment owner; implement cross-owner tests. No GET mutation, secret-bearing query string or cacheable private response.
- [ ] Proposed API surface: enrollment/status, area CRUD, subscription upsert/reconcile, pause/resume, rate-limited test notification and delete-all. Validate request size and allowed fields; return minimal state with `Cache-Control: no-store`. Keep addresses, coordinates, push endpoints, keys and credentials out of URLs, access/error logs, exception traces, usage events and public health output. Review infrastructure logging as well as application logs.
- [ ] Store only what matching/delivery needs: center/radius, provider choices, language, alert preferences, consent/configuration revision, random area/owner IDs, subscription endpoint/key material, lifecycle timestamps and bounded matching/delivery state. Keep typed address/display label local. Encrypt private monitoring coordinates and push material at the application layer with versioned Worker-managed encryption keys; use a coarse spatial index only as needed for candidate selection. Treat that index as private location data too. Plan key rotation/read compatibility and failure behavior; never commit private VAPID/encryption keys.
- [ ] Prevent the push sender becoming an arbitrary-URL fetch proxy: validate subscription scheme/port/length and key shapes, allow only reviewed browser push-service origins, reject credentials/fragments/private/local destinations, and disable redirects. A configurable explicit allowlist has a documented update process for browser compatibility; don't weaken it to arbitrary HTTPS on an error. Duplicate endpoints are detected with a keyed digest without logging the endpoint or merging different owners' areas.
- [ ] Implement a visible enrollment confirmation/test, browser/server reconciliation on app open, permission revocation, expired endpoint cleanup and subscription renewal without relying solely on `pushsubscriptionchange`. Track VAPID key version and support rotation/re-enrollment; an expired subscription does not silently re-prompt the user.
- [ ] Pause stops new evaluation/delivery for the chosen area immediately. Deleting an area removes its remote monitoring state and cancels pending deliveries before removing local data; if offline, show deletion pending and retry explicitly. “Disable all notifications and delete server data” deletes the enrollment/areas/queued work and unsubscribes the browser; deleting the last area disables unused server subscription state. Browser permission itself is managed in browser/OS settings.
- [ ] Accountless data-loss handling: if cookies/local data disappear, the app cannot authenticate deletion of an old enrollment and must not pretend it can. Browser unsubscribe, dead-endpoint cleanup and server lease expiry bound orphan retention. Proposed explicit server lease: 180 days from last authenticated app use/renewal, displayed before enrollment and in settings; sends do not extend it. Expiry stops monitoring and purges service data; reopening offers deliberate renewal. This duration is provisional and must be accepted in the retention ADR.

Exit: owner isolation, CSRF/input validation, endpoint restrictions, sensitive-log tests, encryption/rotation, enrollment reconciliation and genuine deletion/expiry are verified in staging. No public beta before this boundary works.

## Phase 3 — matching, alert state and a durable delivery outbox

- [ ] Run matching only after a complete, healthy source generation is committed. Read provider-qualified published data and versioned geometries through production modules; never scrape the rendered map, poll upstream per subscriber or depend on container runtime writes. Source ingestion succeeds independently of notification matching/delivery.
- [ ] Candidate selection uses coarse spatial buckets/bounding boxes, then verified polygon/radius intersection or point distance. Respect holes/multipolygons, radius and provider coverage; centroid-only distance must not miss a polygon crossing the watched area. A large nearby event is still “nearby,” not an address-service certification. Store coverage/unknown status rather than treating every point as HQ-covered.
- [ ] Maintain per-area/provider baseline, source cursor and observed logical-event set. Evaluate newly eligible events, not every unchanged snapshot. A narrower/wider radius, provider addition or parser change must not replay old observations as new. Keep out-of-order generations from rolling the cursor backward. A new-source activation requires explicit area preference, not automatic enrollment.
- [ ] Offer optional quiet hours (off by default) with a stored IANA timezone, clear local-time preview and DST tests. Quiet hours suppress ordinary sends rather than accumulating a morning flood; at the next eligible window, recheck source/relevance/TTL and coalesce only still-useful information. Show when caps or quiet hours may suppress alerts. Do not request notification time-zone/location data from a third party.
- [ ] Collapse the same logical event affecting overlapping saved areas on one device into one notification linking the relevant areas. Keep independent providers attributed rather than deduplicating by proximity alone. Preserve logical event identity and state history separately from subscriber matches; do not multiply copied event/geometry rows for every area.
- [ ] Atomically persist match cursor changes and a D1 delivery outbox with unique `(enrollment, provider, logical_event, alert_type, eligibility/configuration_revision)` semantics. Replays and interrupted jobs must not lose alerts or manufacture duplicates. Enforce caps/grouping before delivery eligibility; decide what the user will actually receive when many new events arrive together.
- [ ] Initial delivery architecture: bounded D1 outbox batches dispatched by an independently enabled Worker schedule (proposed five minutes), with job leases, cursor/index bounds and a deterministic retry schedule. No in-memory-only `waitUntil` queue. A Queue may be introduced only if measured load justifies it; keep the same idempotent outbox, since [Cloudflare Queues delivers at least once](https://developers.cloudflare.com/queues/reference/delivery-guarantees/).
- [ ] Retries use leases and bounded exponential backoff/jitter; honor provider retry guidance. Drop/expire invalid subscriptions on 404/410, cap 429/5xx retries, flag sender-auth/key failures distinctly and never log plaintext endpoint/key material. Proposed new-outage delivery TTL is 30 minutes from eligibility detection; tune explicitly before release. Recheck current source freshness, relevance, consent/configuration revision and expiry immediately before send, including after a retry or pause/deletion.
- [ ] No storm after downtime: stale generations produce no alert; recovery establishes a baseline when continuity is unknown and shows coverage gaps in the app. Expired/obsolete queued notices are cancelled, not flushed as current warnings. Rate limiting must not hide stale/unavailable status or synthesize restoration.
- [ ] Delivery state distinguishes queued, attempted, push-service accepted, retrying, expired, invalid subscription and cancelled. An accepted send is not proof the device displayed/read it. A crash after provider acceptance but before the D1 acknowledgement can lead to a duplicate: use a stable per-alert notification tag/ID for replacement/coalescing and document best-effort duplicate suppression. Do not claim exactly-once delivery.
- [ ] For later planned alerts: validate actual scheduled times, changes/cancellations, timezone/DST and reminder windows; no stale reminders after a plan is cancelled. For later restoration: require explicit provider resolution or a validated complete-feed absence rule, a source-freshness check and a prior matching alert; never infer household restoration from collection failure or geometry disappearance. These are separate release gates, not hidden first-release behavior.

Exit: deterministic replay reproduces eligibility, gaps and suppression; matching is bounded by measured candidate sets rather than a full subscribers×outages scan; queue/write/send fault tests prove no false all-clear, uncontrolled replay or unbounded duplicate loop.

## Phase 4 — visible push handling and platform verification

- [ ] Extend the existing service worker with visible `push` and `notificationclick` handling while preserving offline fallback and safe update behavior. Validate payload schema/version, language, length and allowed same-origin destinations. Use `event.waitUntil(showNotification(...))`; no silent tracking push or hidden “test” heartbeat. Handle malformed/unavailable details with a generic visible notification rather than failing silently.
- [ ] Payloads contain a generic localized message, provider, opaque alert/area references, observed time, schema version and stable notification tag; no exact address, coordinate, label, management secret or full source record. Browser-transport encryption is required in addition to private server storage. Do not depend on an app-open network fetch to obtain the text needed to display a push.
- [ ] Notification clicks focus an existing same-origin client or open an allowlisted saved-area/detail route. Server-owned opaque references need owner authorization on follow-up reads; they are not bearer access to coordinates. Do not accept arbitrary click URLs. For deleted/expired areas or unavailable data, show a safe explanatory view instead of a false live result; offline views show the observation time and lack of current verification.
- [ ] Preserve the current service-worker registration scope and manifest install identity unless an explicit migration is designed. Review cache/version updates and current controller-change reload logic to prevent lost local state, broken active searches or repeated permission prompts. Notification API responses/private data must never enter public service-worker/CDN caches.
- [ ] Test real end-to-end delivery on Chrome/Edge desktop, Firefox desktop, Safari macOS, Chrome Android and a Home Screen web app on a supported iPhone/iPad. Capability-detected unsupported states stay useful. Local Playwright permission mocks and service-worker fixtures cover logic but cannot prove actual APNs/FCM/Mozilla delivery, background wake, lock-screen text or iOS installation behavior.
- [ ] Include background/closed tab, offline/reconnected device, permission denied/revoked, cleared storage, browser update, VAPID rotation, service-worker upgrade, locale, click navigation, duplicate tag replacement and OS notification-disabled behavior. Do not request critical-alert privileges, override Focus, or promise delivery while the device/OS suppresses it.

Exit: real devices receive a deliberately requested test and a controlled staging event, opening the correct saved area; no sensitive lock-screen content, unexpected permission prompt, broken ordinary map flow or silent claim of guaranteed delivery.

## Phase 5 — operations, costs and staged release

- [ ] Add private aggregate operational metrics: evaluations/cursor lag, candidate counts, matching duration, outbox age/depth, attempts, accepted sends, retries, expiry/cancellation and inactive subscriptions. Avoid endpoint/coordinate/user-level dashboards and tracking pixels/notification-open analytics. Keep this operational store separate from ADR 0007's analytics aggregates; public health exposes only coarse service availability/freshness.
- [ ] Define health alerts for ingestion dependency failure, matcher lag, stuck outbox, send failures and cleanup failure. Do not call successful push-service acceptance “delivered.” A bounded dead-letter/error record contains redacted reason codes and retention, not private payload dumps. Existing operator monitoring should report meaningful state changes, not a notice for each ordinary send.
- [ ] Budget from measured enabled areas, candidate matches and eligible pushes, not page views: D1 reads/writes and storage, encryption/matching Worker CPU, dispatcher invocations, push requests, and any Queue usage. Establish numeric beta enrollment/global send caps and a monthly spend limit before activation; reject further enrollment gracefully when capped. Reuse existing per-IP edge controls only where their actual plan/rule capacity permits; add application owner/global quotas regardless. Do not persist IPs for subscription analytics or assume a free spare rule.
- [ ] Proposed retention: pending outbox through its delivery TTL; redacted terminal delivery/dedup rows for seven days; current match/baseline state only while enrollment is live, plus compact episode/dedup state sufficient to prevent repeat alerts for still-active events; service data purged on explicit deletion/180-day lease expiry or invalidated endpoints. Any aggregate health trends have a stated bounded retention. Queue messages carry only opaque IDs so deleting service data makes queued work unusable. Document backup/log/physical-deletion lag honestly; notification coordinates/endpoints do not belong in permanent R2 raw-source archives.
- [ ] Separate feature controls for local saved areas, enrollment, matching and sending. Deploy additive schema, disabled sender and compatible service worker/readers first. Start with local-only areas, then operator-owned opt-in staging devices, then a small explicitly opted-in beta for at least two weeks including failure/recovery drills. Simulated staging events must never reach production subscriptions. Real-event agreement and user feedback are required in addition to synthetic tests.
- [ ] Public rollout requires the privacy/identity/source gates, real-device evidence, bounded delivery/backlog costs, deletion/expiry proof, current CI/CodeQL results and explicit production deployment authorization. No automatic subscription migration or notification on first launch; users choose the feature.

Rollback: stop sending immediately, keep the pause/delete/settings routes working, and mark notifications temporarily unavailable. Cancel stale queued work so re-enabling cannot trigger a flood. If matching is faulty, stop it independently of ingestion. Keep local saved areas and ordinary HQ/Westmount map reads available; do not delete source history or blindly revert additive migrations. Retain only needed private service data under the published retention rules and continue deletion/expiry cleanup even while delivery is paused.

## Implementation slices and acceptance checks

Proposed independent PRs/worktrees, each with one coding task and no production enablement by default:

1. Product/privacy/retention ADR, source event-identity contract, notification schema and representative labelled fixtures.
2. Browser-local saved areas and minimal existing-sheet controls, usable with no permission/server state.
3. Private enrollment/area APIs, D1 schema, encryption/credentials, ownership/CSRF/endpoint validation and lifecycle cleanup.
4. Pure matching/dedup/caps plus source-generation integration and durable outbox; sender disabled.
5. Worker-compatible VAPID/encrypted sender, bounded dispatcher, service-worker display/click flow and operations controls.
6. Explicitly authorized device/staging tests and opt-in beta, then a separately approved public release.
7. Planned/reminder/restoration options only after their additional semantic and notification-volume gates.

Verification required for touched code:

- Node: event identity across row reorder/version/polygon changes; complete/partial/stale/out-of-order sources; spatial edges/holes/radii; consent revisions; caps/overlap grouping; replay/idempotency; transaction/lease concurrency; cancellation; timeout-after-send ambiguity; expiry/404/410/429/auth errors; SSRF/redirect restrictions; sensitive-log redaction; encryption/key rotation and owner isolation. Use a local/staging D1 integration harness for real transaction/deletion behavior and a local fake push service for deterministic transport failures.
- Python: source/coverage-preserving view models, settings routes and local-only fallback behavior if touched; update both service fakes and their contract test. Templates/JS: French/English, keyboard/screen-reader semantics, desktop/mobile sheet behavior and all permission/enrollment states.
- Playwright: saved areas independent of permission, reload/storage migration, enable/pause/delete, offline pending deletion, source stale/unknown, boundary matches, private-response caching, notification click allowlist and all ordinary search/map/domain/comparison flows. Inspect desktop/mobile screenshots; keep the real-device delivery matrix as separate evidence from browser mocks.
- Run AGENTS.md's format/lint commands and relevant suites; cross-layer implementation needs `uv run pre-commit run --all-files`, `uv run pytest -q`, `node --test tests/*.test.js` and `npm run test:e2e`. Keep dependencies locked/audited; `uv lock` accompanies any pyproject edit. Rehearse migrations, Wrangler dry-run, flags, secrets, lease cleanup and rollback before an authorized real deploy.

Definition of done: useful local saved areas; explicit, understandable opt-in; no unauthorized enrollment read/write or sensitive logs; accurate source/nearby wording; bounded matching/delivery with no replay storm; real-browser/device push and unsubscribe verified; practical costs/retention documented; operational failure detection and rollback proven. End-to-end timing is source cadence plus matching/dispatch plus browser transport, not an instant or emergency alert service.

Sequencing: this can be developed independently of Westmount, starting with local saved areas and HQ-only source validation. Plan several reviewable implementation slices plus a minimum two-week opt-in beta; event-identity/source gaps and real-device availability determine the calendar. Current storage planning remains a prerequisite for unbounded growth. No accounts or cross-device sync are implied by this plan.
